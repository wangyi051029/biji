# 设计说明书

**题目**：面向小样本工业工况预测：融合统计学习的深度学习智能计算优化方案
**课程**：制造智能技术课程设计
**日期**：2026 年 9 月

---

## 一、背景调研（研究意义）

### 1.1 问题背景

工业现场的设备（航空发动机、风机、机床等）在运行过程中，传感器会持续记录温度、压力、转速等工况数据，形成按运行周期排列的时序数据。基于这些数据提前估计设备还能安全运行多久（剩余使用寿命 RUL），是预测性维护的核心问题，直接关系到非计划停机的成本。

实际落地时这个任务有三个绕不开的困难：

1. **标签样本少**。设备故障是低频事件，带标签的退化样本难以大量获取。以常用的公开数据集 C-MAPSS 为例，每个子集的训练发动机只有 100~260 台，属于典型的小样本场景。直接用深层网络训练，很容易把噪声也学进去，造成过拟合。
2. **数据噪声大**。传感器受环境和测量误差影响，数据里混有异常点和随机波动。统计学习里的异常检测、滤波方法正好能处理这一类问题。
3. **硬件算力受限**。工业现场的部署环境大多是普通 PC，没有高端 GPU。深度学习模型如果参数过多，训练慢、推理也慢，难以实际使用。

### 1.2 研究意义

如果把三类方法分开看：纯深度学习对时序特征挖掘能力强，但小样本下容易过拟合，算力开销也大；纯统计学习训练快、对小样本友好，但很难抓住深层的时序退化模式，预测上限有限。把两者结合起来，再叠加模型轻量化手段，理论上可以在"精度尽量不降、算力明显下降"的方向上取得平衡。

本课程设计的目标，就是在普通 PC（CPU）上验证这条融合路线是否可行：用统计学习把数据处理干净、把评估做扎实，用深度学习学习退化规律，再用剪枝和量化把模型压小，最后通过对照实验给出量化结论。这个验证过程本身对理解"小样本 + 边缘部署"的现实问题有一定参考价值。

### 1.3 相关工作

- C-MAPSS 数据集（NASA 商用模块化航空推进系统仿真）是 PHM / RUL 预测领域使用最广的公开基准，最早出自 Saxena 等在 PHM08 会议上的工作；
- 深度时序模型用于 RUL 预测的主流选择是 LSTM、GRU 等循环网络，LSTM 对长周期退化趋势的建模能力已得到较多验证；
- 模型轻量化方向主要有剪枝、量化、知识蒸馏等，相关综述可见李威等的《深度学习模型轻量化与智能计算优化综述》；
- 小样本场景下引入统计学习手段（交叉验证、方差分析、异常检测）改善训练，在小样本学习综述（何清等）中有系统讨论。

## 二、方案设计

### 2.1 设计目标与约束

- **功能目标**：一套 B/S 架构的设备工况预测系统，能完成"数据 → 建模 → 优化 → 预测 → 对比"的完整流程，并支持手工输入传感器数据进行测试；
- **硬件约束**：全部实验在普通 PC 的 CPU 上完成，不依赖 GPU；
- **质量约束**：自动化测试全通过，数据来源链接有效，实验过程可一键复现。

### 2.2 方案比选

初步考虑过三个方案：

| 方案 | 思路 | 主要问题 |
|------|------|----------|
| A | 只用深度学习（LSTM 端到端） | 小样本下过拟合风险高；训练和推理算力开销大，普通 PC 上表现不稳定 |
| B | 只用统计学习（回归、滤波等） | 训练快、解释性好，但对时序深层特征挖掘不足，预测精度上限低 |
| C | 统计学习 + 深度学习 + 智能计算优化 | 三者分工：统计学习管数据和评估，深度学习管建模，优化管轻量化 |

最终选 C。理由很直接：三个技术方向正好对应任务书对"技术方向"的要求，更重要的是，这个组合在工程上是自洽的——统计学习解决"数据不干净、样本少"的问题，深度学习解决"模式学不出来"的问题，优化解决"模型跑不动"的问题，各管一段，不冲突。

### 2.3 总体架构

系统按"数据 → 模型 → 优化 → 验证 → 输出"五层规划，落地上采用 B/S 四层结构：

```
前端 Web UI（HTML/CSS/JS + ECharts）
        │ REST API
FastAPI 后端（服务层）
        │
├─ 算法层：statistical.py（统计学习）
│          deep_learning.py（深度学习）
│          optimization.py（智能计算优化）
└─ 数据层：SQLite（datasets/models/predictions/experiments 四表）
           data/raw 原始数据、data/processed 预处理结果、data/models 模型权重
```

### 2.4 技术选型

| 组件 | 选型 | 理由 |
|------|------|------|
| 编程语言 | Python 3 | 数据科学和 AI 生态最成熟 |
| 深度学习框架 | PyTorch（CPU 版） | 可以方便地自定义剪枝、量化逻辑；CPU 版安装体积小 |
| 统计学习 | scikit-learn、scipy | 特征筛选、交叉验证、假设检验都有现成实现 |
| 后端 | FastAPI + Uvicorn | 轻量、自带接口文档，适合课程设计规模 |
| 数据库 | SQLite | 零配置单文件，演示场景足够 |
| 前端 | 原生 HTML/CSS/JS + ECharts | 无构建依赖，任何浏览器打开即用 |

## 三、数据集构建

### 3.1 数据集选择

选用 NASA C-MAPSS 涡扇发动机退化仿真数据集。选它的原因：

- **任务契合**：数据就是"按周期记录的传感器时序 + 剩余寿命标签"，正是本课题要预测的对象；
- **小样本属性**：每个子集只有 100~260 台训练发动机，天然是小样本；
- **含噪声**：数据中混有传感器噪声，适合展示统计学习的数据处理作用；
- **公开可复现**：PHM 领域经典基准，别人能对照验证。

### 3.2 数据来源与可用性验证

数据规模约 44MB，包含 FD001~FD004 四个子集，每台发动机 3 个运行设置参数 + 21 路传感器测量。

来源链接的处理有个小插曲：NASA 原来的下载直链已经失效（页面 404），我改用了 PHM Society 的官方镜像地址，并用 HTTP 请求逐一验证可访问后才写进说明文档：

- 数据包直链：`https://phm-datasets.s3.amazonaws.com/NASA/6.+Turbofan+Engine+Degradation+Simulation+Data+Set.zip`（已验证 HTTP 200）
- 官方页面：`https://data.phmsociety.org/nasa/`

原始数据放入仓库 `data/raw/`，每个子集三个文件（train/test/RUL 标签），数据来源说明见 `data/数据来源说明.md`。

### 3.3 数据集规模

| 子集 | 训练单元 | 测试单元 | 原始传感器数 | 工况数 |
|------|---------|---------|------------|--------|
| FD001 | 100 | 100 | 21 | 单工况 |
| FD002 | 260 | 259 | 21 | 多工况 |
| FD003 | 100 | 100 | 21 | 单工况 |
| FD004 | 248 | 249 | 21 | 多工况 |

### 3.4 预处理设计（统计学习方法）

预处理逻辑独立成 `code/preprocess.py`（命令行脚本），同时在系统内以 `backend/algorithms/statistical.py` 提供同样的函数，两者逻辑一致。整条流水线七步：

**① 数据清洗。** 先检查缺失值，再把方差几乎为 0 的常值传感器剔除。C-MAPSS 本身没有缺失值；常值传感器（如 FD001 的 s1、s5、s10、s16、s18、s19）不携带退化信息，留着只会增加模型输入维度。

**② 噪声识别。** 用 IQR 准则和 Z-score 准则双重标记异常点：IQR 取 Q1-3×IQR 到 Q3+3×IQR 为正常区间，Z-score 取 |z|>6 为异常。这里阈值取得比较宽，目的是只标记明显异常、不误伤正常波动。识别的结果只作为数据质量指标记录（每行打 is_noise 标记），不删除样本——因为删数据在小样本场景下代价太高。

**③ 特征筛选。** 三层递进：先做标准化后的方差分析，剔除低方差特征（阈值 1e-3）；再做相关性分析，剔除 |r|>0.95 的冗余传感器（成对出现时保留与 RUL 相关性更高的一侧）；最后对每个保留特征按寿命阶段分组做单因素 ANOVA，p<0.05 才保留。筛选结果 FD001→14 个特征、FD002→4 个、FD003→14 个、FD004→6 个，和 PHM 领域常见结论一致。

**④ RUL 标签构造。** 用分段线性函数：`RUL = min(max_cycle - cycle, 125)`，寿命上限取 125 个循环。原因是早期健康阶段的 RUL 标签动辄几百，数值过大且缺乏区分度，截断后模型更容易学。

**⑤ 数据划分。** 按发动机单元划分，每台单元最后 20% 周期划作测试集，再随机抽 15% 的单元做验证集，其余为训练集。保证同一台发动机的数据不会同时出现在训练和测试里，避免数据泄漏。

**⑥ 交叉验证。** GroupKFold 5 折，按单元分组，同一台发动机只落在同一折。这样评估的是模型对"没见过的新发动机"的泛化能力，而不是对数据片段的记忆。

**⑦ 标准化。** StandardScaler 只在训练集上拟合均值和方差，再应用到验证集和测试集。这也是防泄漏的关键一步，如果拿全量数据拟合标准化参数，验证结果会偏乐观。

### 3.5 预处理结果

| 子集 | 原始传感器 | 筛选后特征 | 训练样本 | 验证样本 | 测试样本 | 噪声率 |
|------|----------|-----------|---------|---------|---------|--------|
| FD001 | 21 | 14 | 14024 | 2444 | 4163 | 5.93% |
| FD002 | 21 | 4 | 36651 | 6254 | 10854 | 15.9% |
| FD003 | 21 | 14 | 16825 | 2910 | 4985 | 15.3% |
| FD004 | 21 | 6 | 42004 | 6899 | 12346 | 15.4% |

四个子集均无缺失值，标准化后均值≈0、方差≈1。预处理产物（干净数据 CSV、特征筛选明细、交叉验证折索引、标准化参数）统一写入 `data/processed/<子集>/`，并同步登记到 SQLite 的 datasets 表。

## 四、三个技术方向的详细设计

### 4.1 技术方向一：统计学习

**定位**：数据层，负责把原始数据变成模型能直接吃、评估又可信的数据。

**模块**：`backend/algorithms/statistical.py`，核心函数与设计如下：

- `detect_missing` / `detect_constant_sensors`：缺失值与常值传感器检测。常值判定用方差 < 1e-12。
- `detect_noise`：IQR + Z-score 双准则噪声识别，返回每个传感器一列的噪声标记和汇总的 is_noise。实现时对常值列做了跳过处理，避免 zscore 对零方差列产生数值警告。
- `feature_selection_pipeline`：方差 → 相关 → ANOVA 三层筛选，输出保留特征列表和每层剔除明细。
- `make_rul_label`：分段线性 RUL，cap=125。
- `split_train_val_test`：按单元划分，测试取每台最后 20% 周期，验证取 15% 单元。
- `group_kfold_indices`：GroupKFold 5 折索引。
- `fit_scaler` + `preprocess_pipeline`：把上面步骤串成一条流水线，返回 (标准化后的划分, 元信息, scaler)。

设计上的一点考虑：所有统计量（方差、相关、ANOVA、标准化参数）都只在训练部分上计算，测试部分只做变换。这样下游所有实验的泛化指标才是可信的。

### 4.2 技术方向二：深度学习

**定位**：模型层，负责从时序数据中学习退化模式，输出 RUL 预测。

**模块**：`backend/algorithms/deep_learning.py`。

**样本构造（滑动窗口）**。按发动机单元分组后按 cycle 排序，用窗口长度为 30、步长为 1 的方式切样本。每个样本是最近 30 个周期的特征序列，标签是该窗口最后一个周期的 RUL。窗口取 30 是考虑到退化的惯性一般能持续几十个周期，太短信息不足，太长则样本数急剧减少（小样本场景伤不起）。

**网络结构**：

```
输入 (batch, 30, n_feat)
  → LSTM(input_size, hidden=96, num_layers=2, dropout=0.2, batch_first=True)
  → 取最后时刻输出 (batch, 96)
  → Linear(96→32) → ReLU → Dropout(0.2)
  → Linear(32→1)
  → 输出 RUL（预测后 clip ≥ 0）
```

hidden 取 96、两层 LSTM，是精度和训练速度之间的折中——再大在 CPU 上训练就很慢了。

**训练策略**：

- 优化器 Adam，lr=1e-3，weight_decay=1e-4（L2 正则，抑制过拟合）；
- 损失函数 SmoothL1Loss（Huber），对异常点不如 MSE 敏感，和小样本数据里的噪声更匹配；
- ReduceLROnPlateau 学习率调度，patience=2、factor=0.5，验证损失不降就减半学习率；
- 早停 patience=5，验证损失连续 5 轮不改善就停止，并回滚到最优权重；
- 梯度裁剪 clip_grad_norm=1.0，防止梯度爆炸；
- 固定 torch.manual_seed(42) 和 np.random.seed(42) 保证可复现。

**评估与持久化**。evaluate 输出 MAE/RMSE；推理耗时用同一批样本重复推理 5 次取平均。保存时把架构参数（input_size/hidden_size/num_layers/window）一并写进 .meta.json，加载时按 meta 重建模型，从根上避免"权重和结构对不上"这一类问题。

### 4.3 技术方向三：智能计算优化

**定位**：优化层，在训练好的模型上做轻量化，降低存储和计算开销。

**模块**：`backend/algorithms/optimization.py`。

**模型剪枝**。采用基于权重幅值的非结构化剪枝：对每个权重张量，把 |w| 最小的 30% 置零（阈值取权重绝对值分布的 30 分位）。偏置（维度 < 2 的参数）不参与剪枝，因为偏置数量少、置零影响大。剪枝后的稀疏权重直接保留在模型中参与推理。

**参数量化**。对剪枝后的模型做 int8 线性量化模拟：对每个权重张量按 min-max 求 scale 和 zero_point，量化到 0~255 整数再反量化回浮点。实现里有一个关键细节：反量化前先用 `masked_fill` 把剪枝产生的精确零值恢复成 0。如果不做这一步，量化会把那些"本来应该是 0"的权重变成非零小数，剪枝的效果就白做了——这个问题在调试阶段实际踩到过，后面调试章节会细说。

**学习率调度**。优化模块同时提供 cosine 退火和阶梯衰减两种调度器，作为训练策略优化的可选手段，实际训练默认走 ReduceLROnPlateau。

**压缩对比**。`compare_models` 对基准模型和优化后模型做同口径对比：参数量按非零参数计（剪枝生效）、模型体积按量化位数计（int8 则每参数 1 字节）、推理耗时同批数据实测、精度指标可选。最后输出参数量下降率、体积下降率和推理加速比。

## 五、界面设计

### 5.1 总体设计

系统是 B/S 架构，前端用原生 HTML/CSS/JavaScript + ECharts 实现，无任何构建步骤。整体配色偏深色专业风格，左侧功能导航，右侧内容区，单页应用通过标签页切换七个功能页面。所有页面通过 REST API 与后端交互，数据来自 SQLite 数据库和预处理产物。

### 5.2 页面功能设计

1. **总览**：顶部四张指标卡片（数据集数、模型数、预测记录数、总样本数），下方两张图——特征筛选柱状图和模型推理耗时对比图，一进系统就能看到全局状态。
2. **数据管理**：下拉选择子集，点"预处理"按钮执行统计学习流水线，下方展示已入库数据集表格（规模、特征数、噪声率）和特征筛选明细。
3. **模型训练**：配置子集、窗口、隐层、训练轮数、学习率等超参数，点击训练后展示返回的模型指标（参数量、MAE/RMSE、推理耗时），训练过的模型列表实时刷新。
4. **智能优化**：选择模型、剪枝比例、量化位数，执行后展示剪枝统计、量化参数和雷达图形式的压缩效果对比。
5. **在线预测**：选子集、选模型、输入发动机单元号，后端读取该单元最后 N 个周期数据，预测 RUL 并显示结果，同时预测记录入库。
6. **手动测试**：面向"我手里只有一段传感器读数"的场景。页面根据所选模型的元信息动态生成特征输入表单，可以一键填入从原始数据中抽取的示例读数，也可以手动粘贴 CSV 格式数据（每行一个周期、逗号分隔）。提交后前端按固定特征顺序组装请求，后端用该子集的 StandardScaler 标准化、补齐窗口后预测 RUL。这条链路把"标准化参数"从预处理阶段一路复用到了预测阶段，保证手动输入的数据和训练数据在同一分布上。
7. **对比分析**：基准模型 vs 优化后模型指标并排对比（参数量、体积、推理耗时、MAE），给出优化结论。

### 5.3 手动测试页的交互细节

手动测试页是后期加的需求。最初只提供在线预测（从数据集选单元），但答辩场景里评委更可能直接问"我随便给你一段数据能不能测"。设计上做了三点：

- 后端提供 `GET /api/model/info/{model_name}`，返回模型的特征列表、窗口长度和一行示例读数，前端据此动态生成输入框，不写死任何特征；
- 前端在"开始预测"前校验行数和列数，列数不对时后端返回 400 并提示期望的特征顺序，避免"数据格式错误但报错信息看不懂"；
- 手动输入的预测记录以 unit=0 入库，与数据集单元的记录区分开，界面上标注"手动输入数据测试（非数据集单元，RUL 仅供参考）"，防止演示时被误读为有标签的真实验证。

### 5.4 离线单文件测试站

完整系统需要 Python 环境才能跑，为了做到"任何电脑双击就能用"，额外做了一版离线单文件站（`offline_rul_site.html`）。构建脚本 `build_offline_site.py` 把 FD001 模型权重和标准化参数 base64 内嵌进单个 HTML，用纯 JavaScript 实现了 LSTM 的前向推理（矩阵乘、sigmoid/tanh 激活、逐层计算），全部计算在浏览器本地完成。界面保留数据输入、示例数据、预测结果展示，并给出特征顺序说明。构建时和 Python 端逐位对过数值：同一输入下 JS 推理结果与 PyTorch 输出误差小于 1e-5，说明 JS 端实现没有引入逻辑错误。

### 5.5 云端完整版

另外把完整功能（七个页面）用 Streamlit 重写为 `app_streamlit.py` 并部署到 Streamlit Community Cloud，网址 https://rul-system.streamlit.app/，浏览器直接访问，不用装任何东西。云端部署的依赖约束（torch 走 CPU 源）在 requirements.txt 里单独注明。

## 六、调试

### 6.1 调试手段

- **自动化测试**：pytest 覆盖统计学习、深度学习/优化、数据库、API 四层，最终 29 项全部通过（`bash run_tests.sh`）；
- **接口级验证**：启动 uvicorn 后用 curl 逐个验证接口，重点看异常路径（列数不匹配、空输入、模型不存在）返回的 HTTP 状态码和错误信息；
- **浏览器端到端**：从总览到对比分析走完整个业务闭环，观察页面渲染和预测结果入库情况。

### 6.2 过程中遇到的主要问题

按时间顺序记录几个印象比较深的：

1. **PyTorch 环境反复丢失**。开发环境是沙箱，后台进程和 pip 包会被周期性清理，torch 和 pytest 前后丢了四次。每次恢复要重装 CPU 版 torch（`pip install torch --index-url https://download.pytorch.org/whl/cpu`）。这个问题也直接推动了"离线单文件站"和"云端部署"两条交付路径——不能假设运行环境一直可用。

2. **模型保存/加载结构对不上**。第一次训练时 hidden 用了 96，但加载代码里重建模型用了默认的 hidden=64，导致 load_state_dict 报 shape 不匹配。修法是把架构参数写进 meta.json，加载时先读 meta 再建模型。之后无论 hidden 怎么改都不会再出现这个错。

3. **剪枝后参数量减少率显示为 0**。剪枝确实把权重置零了，但量化函数反量化时把零权重变成了非零小数，按"非零参数"统计时剪枝效果被抹掉了。修法是量化时保留零掩码，反量化后用 masked_fill 把零位恢复成精确 0。这个 bug 暴露了一个设计问题：剪枝和量化两个步骤必须知道彼此的存在，统计口径（非零参数、按位宽算体积）也要保持一致。

4. **预处理输出混入未筛选列**。早期版本把全部原始列都写进了 CSV，训练时特征维度与筛选结果对不上。改为只输出"筛选后特征 + RUL + 噪声标记"后解决。

5. **FastAPI 新版 TestClient 不触发 startup**。旧版 TestClient 会自动触发 startup 事件建表，新版不会，导致测试里查不到表。改用 lifespan 事件 + 测试 fixture 显式建表后稳定。

6. **手动预测无真值时误差计算崩溃**。手动输入的数据没有真实 RUL，入库时 `abs_error = pred - true_rul` 对 None 直接抛 TypeError。改成 `true_rul or 0` 兜底后修复，同时新增了对应测试。

7. **离线站 JS 推理输出 NaN**。第一版把 LSTM 的 bias 转成了列向量参与矩阵乘，广播维度对不上，输出全是 NaN。改回一维数组后数值立即正常——这类纯数值 bug 光看代码很难发现，靠的是和 Python 端逐位对比才定位到。

8. **公网网址反复失败**。一开始想用 cloudflared 隧道把本地 8000 端口映射成公网地址，试了三次（三个 trycloudflare 域名），要么连接重置、要么返回 HTTP 000，用户端实测报 Error 1033。原因是沙箱环境会周期性清理后台进程，常驻服务根本活不长。这条路走不通后，把方案切换成"离线单文件 + GitHub Pages + Streamlit 云部署"，彻底绕开了"需要常驻服务"这个约束。

### 6.3 实验验证（FD001 演示子集）

在普通 CPU 上训练并优化 FD001 模型，实测结果：

| 指标 | 基准模型（LSTM） | 优化后（剪枝30% + int8量化） | 变化 |
|------|----------------|---------------------------|------|
| 参数量 | 121.03 K | 85.23 K | -29.6% |
| 模型体积 | ~484 KB | ~85 KB | -82.4% |
| MAE | 12.06 | 10.33 | 基本持平（略降） |
| 推理耗时 | 0.06 ms | 0.13 ms | 同量级 |

结论：剪枝 + 量化在几乎不损失精度的前提下，把模型参数减少约 30%、存储减少约 82%，验证了融合方案"降低算力开销、保持精度"的目标。推理耗时没有下降，主要是当前是模拟量化（权重仍是浮点存储），真实加速需要 int8 推理后端，这个留到展望里说。

## 七、总结与展望

### 7.1 成果

- 完成了一套 B/S 架构的设备工况预测系统：统计学习预处理 → LSTM 建模 → 剪枝量化优化 → 在线预测 → 对比分析，七个功能页面全部可操作；
- 三个技术方向都有实质代码和实验支撑，不是装饰性引入；
- 29 项自动化测试全部通过，数据来源、预处理、训练、优化全程入库并纳入 Git 管理，可从零复现；
- 交付了多种使用形态：本地一键运行、离线单文件测试站（双击即用）、GitHub Pages 在线测试站、Streamlit 云端完整版、答辩 PPT 与演示视频。

### 7.2 不足

- 主要实验集中在 FD001 单工况子集，FD002/FD004 多工况子集只完成了数据预处理，没有做模型实验；
- 量化是模拟量化，模型在磁盘上变小了，但推理时仍是浮点运算，没有拿到真正的推理加速；
- 训练样本做了抽样控制（默认 60 个窗口样本），是为了在普通 CPU 上快速演示，和全量训练相比精度有差距；
- LSTM 的训练仍偏慢，batch 和窗口参数没有系统调过。

### 7.3 展望

- 多工况子集上引入迁移学习（先用 FD001 预训练，再微调 FD002/FD004），缓解多工况样本不足的问题；
- 用 torch.quantization 做真实的 int8 推理，把体积优势转成推理加速；
- 尝试注意力机制或 Transformer 类模型，看能否在小样本下进一步压精度；
- 接实时数据流和告警推送，把系统从"演示闭环"推向"能用"。
